## The one thing to read first

**The shot count is still not stable, and I have not fixed it yet.**

Measured on `lv_0_20240407105341.mp4` (17 real shots), three cold-start passes:

```
pass 1  shots=17  355s
pass 2  shots=17  353s
pass 3  shots=10  374s
counts=[17,17,10] UNSTABLE
```

Pass 3 ran while `npm run build` was using the CPU — my own contamination, twice
over, because I had already made that mistake earlier in the night. But the
contamination **is** the finding: the coarse pass plays the clip in real time
and analyses whatever frames the browser presents, so under CPU load it gets
fewer, and any rep inside the gap is never bracketed. The count follows machine
load. A coach pressing the button twice must get the same number.

**Root cause found and half-fixed:**

1. *Fixed and committed* (`5250c83`): nothing ever waited for the video to
   buffer. `preload='auto'` was set and the coarse pass began as soon as
   metadata arrived, so playback raced the download. Cold cache gave 7 shots,
   warm gave 17. `awaitBuffered()` now finishes the download first.
2. *Written, NOT yet applied* (`audit-out/gen-recover.py`): find the temporal
   gaps in the frames the playback pass actually captured, and re-read only
   those windows by exact seek. A clean pass finds no gaps and pays nothing; a
   loaded pass pays for exactly what it lost. Held back deliberately so it
   could not contaminate the six-clip sweep that was running.

Do **not** tune detection thresholds against this. The thresholds are not the
problem; frame delivery is.
