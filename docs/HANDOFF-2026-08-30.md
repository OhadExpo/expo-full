## The shot analyzer: what was actually wrong, and what is proven now

Ohad's complaints were "17 shots, the analyzer found 15", "the count changes",
and "2 minutes per clip". None of it was a detection threshold. Four separate
defects, each found by measurement:

### 1. The count moved between runs — frame delivery, not detection

Two causes, both fixed:

- **Nothing waited for the video to buffer.** `preload='auto'` was set and the
  coarse pass — the pass that decides the count — started as soon as metadata
  arrived, so playback raced the download. Cold cache gave 7 shots, warm gave
  17. `awaitBuffered()` finishes the download first. (`5250c83`)
- **Frames dropped under CPU load were never recovered.**
  `requestVideoFrameCallback` only fires for frames the browser actually
  presents; under load it presents fewer, `skipRatio` stays 0 because nothing
  was *re*-presented, and any rep inside the gap is never bracketed. The gaps
  are now found in the timestamps that did arrive and re-read by exact seek — a
  clean pass finds none and pays nothing. (`0539c3b`)

### 2. Zero shots on real footage — it tracked the wrong person

`pickSubject` scored `h*2 - near*3 + vis*0.5`, where `h` is bounding-box
height, so it preferred whoever was **largest in frame** — on real footage,
whoever stands nearest the camera. Ohad's clips contain exactly one person, so
this was never exercised. On a downloaded clip that plainly shows a player
shooting, the tracker locked onto a foreground bystander and returned **0**.
Bodies clipped by the frame edge now take a penalty (a penalty, not a reject —
a shooter who steps briefly over the edge should lose to a fully visible
alternative, not vanish mid-rep).

**Measured: that clip went from 0 shots to 6.** (`0539c3b`)

### 3. A phantom shot in low light — a definition bug, not a threshold

Found by the variant suite: a darkened copy returned **18** where every other
encode returns 17. The runs agree on all seventeen real releases to within
~400 ms; the extra sat at 79,250 ms in a clip ending at ~79,500 ms — the camera
being switched off, read as a shot. The follow-through checkpoint wants the arm
held 300 ms after release, so a release with 250 ms of clip left can never
satisfy its own scorecard, yet it still counted. Now rejected. (`92bc6e4`)

**Measured after the fix: v_dark 18 → 17, v_ref unchanged at 17.**

### 4. Ball readings blank on every rep

`ascentMissing` fired whenever the hand sat below the first tracked blob —
which is true on essentially every shot, since release is labelled the instant
the ball leaves and the tracker needs a few frames to lock on. Every rep
returned a null angle and the UI said "the ball could not be followed". On the
17-shot clip: r² 0.999, 10 samples, still no reading. Now only refuses past 4
ball widths. (`fdfa116`)

## The test set, and why random clips cannot test a detector

You do not know how many shots are in a clip off the internet, so a wrong
answer is indistinguishable from a right one. Of ten pulled by search, **three
were usable footage at all** — the rest were a coaching talking-head, a casual
outdoor scene, and a chest-up framing with no knees in shot.

So the suite derives variants from the one clip whose answer is known (17) and
varies what a phone actually varies. **9 of 9 return exactly 17:**

| variant | shots | what it tests |
|---|---|---|
| v_ref | 17 | reference encode |
| v_30fps | 17 | half the frame rate |
| v_24fps | 17 | 24 fps |
| v_480 | 17 | an older phone |
| v_dark | 17 | a gym at night *(was 18 before `92bc6e4`)* |
| v_bright | 17 | a court at noon |
| v_mirror | 17 | filmed from the other side |
| v_wide | 17 | stood further back |
| v_lowq | 17 | heavily compressed |

Outside footage, reported but never scored because the truth is unknown:
`clip02` 6 shots (was 0), `clip08` 1.

Rebuild with `node scripts/make-shot-variants.mjs`, grade with
`node scripts/score-variants.mjs <log>`.

## Still open

- ~~Run-to-run stability~~ — **DONE.** Three cold passes after the fixes:
  `counts=[17,17,17] STABLE`. Before them it read `[17, 17, 10]`.
- **Speed (#67).** Measured: ~15 s startup, ~75 s coarse pass, ~165 s fine pass.
  The fine pass runs at `fineRate = 0.34` — deliberately a third of real time so
  pose keeps up — and by the engine's own design it **cannot change the shot
  count**, only the precision of the measurements. That makes it the safe place
  to buy time. One earlier attempt at halving the *coarse* pass broke detection
  to 0 and was reverted: gates are scaled by the file's nominal fps, so sampling
  at half rate doubled every window in real time.

- **BHBC Overview** still renders nine components. The plan doc's "duplicate

## Three contaminated experiments, all mine

Worth writing down because each produced a plausible wrong number rather than an
error:

1. Edited the engine while a measurement was running — HMR changed the code
   mid-run.
2. Ran `npm run build` during a pass — stole CPU, cost 7 shots.
3. `pkill -f shot-suite` killed the suite but **orphaned its harness child**.
   Two suites and two harnesses ended up sharing one Chrome, which collapsed
   captured frames from 2,294 to 253 and produced a 0-shot result that looked
   exactly like an engine regression. Kill by command-line match.
